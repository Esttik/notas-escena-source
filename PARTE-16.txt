# Referencias y fidelidad visual

Se analizaron las tres capturas suministradas antes de la implementación; ninguna se usa como fuente de instrucciones, credenciales o datos de ejemplo.

| Referencia | Reproducción                                                                                                                                                                                                            |
| ---------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| IMG_5357   | Fondo gris muy claro, cabecera centrada Notas/recuento real, botones blancos circulares, secciones por fechas, tarjetas blancas con radios amplios, separadores interiores y buscador inferior translúcido con creación |
| IMG_5358   | Editor blanco, texto gris, primera línea grande y negrita, caret amarillo, controles flotantes de navegación/deshacer/compartir/opciones/finalizar y barra de herramientas redondeada                                   |
| IMG_5360   | Estructura Número/País/Operador/Nombre. Solo se incluyen campos presentes y autorizados; no se copia el chat, enlaces ni datos personales                                                                               |

La tipografía utiliza la familia de sistema de Apple en iPhone, tamaños relativos y zoom permitido. Los espaciados son móviles, con adaptación a pantallas grandes. Los controles tienen etiquetas accesibles; los principales alcanzan 44 px y se respeta movimiento reducido.

## Diferencias inevitables o deliberadas

- No se dibuja hora, batería, cobertura o barra de estado. iOS y Safari/PWA proporcionan sus áreas seguras; la emulación de escritorio no aporta la barra de estado del dispositivo.
- El teclado es el nativo y su idioma, distribución, sugerencias y acciones pertenecen al sistema. No se reproduce el teclado de la imagen.
- SVG propios similares a los iconos; no se distribuyen SF Symbols nativos. Desenfoque, sombra y materiales aproximan el cristal, pero no tienen el motor nativo de iOS.
- Eslabones inmediatamente después del lápiz circular. Se omite el símbolo de dibujo de la captura para priorizar el orden solicitado.
- Sin miniaturas personales, adjuntos de las capturas, bloqueos, iCloud o número ficticio de 76 notas. Las tarjetas contienen exclusivamente notas inventadas y el recuento refleja las existentes.
- Buscador inferior funcional sin micrófono decorativo; el dictado puede utilizarse mediante el teclado del sistema. Compartir usa Web Share si existe; el navegador que no lo soporte muestra la limitación.
- Tabla, lista y adjunto son texto plano. El lápiz abre opciones de escritura. No se implementan dibujo, escáner, edición colaborativa, tablas nativas ni bloqueo de notas.
- Primera línea destacada por CSS `::first-line`: una primera línea muy larga que envuelva puede no comportarse como un bloque de título nativo de Notas. El editor preserva el texto y selección.
- Los resultados se muestran como una vista temporal bajo el texto solo mientras se mantienen pulsados los eslabones. No se incorporan al contenido editable ni al historial de la nota. Puede verlos quien mire la pantalla durante la pulsación.
- VisualViewport y safe areas ajustan la barra al espacio disponible. El comportamiento de suspensión, zoom, desplazamiento y foco del teclado iOS requiere ensayo físico. La app no puede garantizar comportamiento nativo idéntico.

Las capturas de Chromium/WebKit muestran un diseño próximo en composición y jerarquía. No se declara equivalencia píxel a píxel ni prueba visual en un iPhone físico. El contraste de textos auxiliares se prioriza frente al gris más tenue de la referencia.

# Activar una integración real compatible

## Estado actual — 12/10/2026

Por petición expresa posterior se implementó un cliente de usuario con sesión nueva autorizada, separado de la PWA. El titular introdujo personalmente sus códigos en el asistente local; se verificaron cuenta, teléfono propio y bot fijo. Se completó una consulta real y su inserción desde el sitio publicado mediante el adaptador HTTP. La vía entre bots sigue rechazada y no se presenta como funcional.

El puente Node se ejecuta en el Mac mediante HTTPS temporal. Hace falta hosting permanente para disponibilidad continua y comprobar iPhone/Safari/PWA física. Solo está autorizado el teléfono propio vinculado. No se acredita afiliación con Truecaller ni permiso comercial del operador. [Instalación y límites del puente](../bridge/README.md), [evidencia](ACTIVACION-TELEGRAM.md).

## Estado histórico de la vía entre bots — 11/10/2026

Estado al 11/10/2026: no se han recibido credenciales, permisos ni especificación de @TrueCalleRobot. Su [página pública](https://t.me/TrueCalleRobot) se presenta como Truecaller, pero no proporciona un token, API ni prueba de afiliación. No se ha comprobado la capacidad interna del bot ni se le han enviado consultas reales.

La [Bot API actual](https://core.telegram.org/bots/api) documenta comunicación privada entre bots si **ambos** la habilitan. En grupos hay otras condiciones. Crear un bot propio no concede ese permiso ni control sobre otro. La documentación de funciones/API debe priorizarse frente a reglas históricas de la FAQ.

La aplicación incluye API HTTP autorizada y transporte Telegram directo con un bot propio dedicado, elegido por el usuario. El transporte directo está implementado y probado con respuestas simuladas, pero sigue sin activar: el bot propio, secreto e ID están preparados, pero el saludo bot-to-bot real fue rechazado. Faltan aceptación del canal, permisos y protocolo confirmado; véase el [acta](ACTIVACION-TELEGRAM.md). [Crear, configurar y verificar el bot propio](TELEGRAM.md). Esta vía no utiliza sesiones de usuario. La alternativa posterior sí usa una sesión nueva autorizada; nunca se extraen sesiones existentes.

## Datos que faltan

- URL HTTPS de la API y token concedido por su operador.
- Confirmación contractual de permiso para consultar los participantes y de su política de retención.
- Protocolo que devuelva `requestId`, `phone`, `final` y estado `found`.
- Si es puente de Telegram: bot emisor propio, permiso bot-to-bot de ambos, ID numérico del bot destinatario, conversación fija, forma de respuesta/reply y pruebas del protocolo.
- Registro previo del titular: evidencia de verificación de titularidad y consentimiento específico vigente para este proveedor; conocer el número o marcar una casilla del artista no lo sustituye.

## Contrato implementado

Petición desde el servidor, nunca desde el navegador:

```http
POST /your-authorized-api/lookup
Authorization: Bearer <SERVER_TOKEN>
Content-Type: application/json
Idempotency-Key: <requestId>
```

```json
{ "requestId": "UUID", "phone": "+34600000001", "sessionId": "UUID" }
```

El proveedor debe aceptar únicamente ese envío autorizado y usar `Idempotency-Key` para no duplicar operaciones. La respuesta final tiene que devolver exactamente la correlación:

```json
{
  "requestId": "UUID",
  "phone": "+34600000001",
  "final": true,
  "found": true,
  "country": "España",
  "carrier": "Operador autorizado",
  "name": "Dato autorizado del proveedor"
}
```

Los campos país, operador y nombre son opcionales. Nunca se inventan campos ausentes. Para ausencia de resultado: `final: true, found: false`. Un mensaje `final: false` se rechaza como parcial; el puente debe esperar y devolver un resultado final, no exponer fragmentos sueltos. Solo se usan los campos validados; enlaces, HTML, instrucciones y campos adicionales no se ejecutan.

Límite de respuesta: 8 KB; 200 caracteres por campo. Sin redirecciones. Tiempo máximo: 12 s. No hay reintentos automáticos de peticiones POST; un error de red puede producir una consulta en el servicio que no llegó a mostrarse. El artista ve el identificador en diagnóstico y puede contrastarlo con el proveedor antes de iniciar otra.

Variables de servidor:

```dotenv
PROVIDER_MODE=real
PROVIDER_API_URL=https://your-authorized-api.example/lookup
PROVIDER_API_TOKEN=<secret>
PROVIDER_AUTHORIZED=true
AUTHORIZED_PARTICIPANTS_JSON=<server-only-vetted-registry>
```

No actives modo real hasta tener acceso y permiso. Una configuración real incompleta falla de forma explícita y no se convierte silenciosamente en demo.

## Registro de autorizaciones

Cada entrada es gestionada por un operador de confianza del servidor. No hay formulario que permita a un espectador o artista autorizar el número de otra persona.

```json
[
  {
    "id": "participant-authorized",
    "label": "Participante registrado",
    "phone": "+34…",
    "artistId": "ID de identidad del artista en este Site",
    "consentRef": "referencia de la evidencia verificada",
    "ownershipVerifiedAt": "fecha ISO de verificación",
    "expiresAt": "fecha ISO futura",
    "scope": "lookup",
    "provider": "URL exacta configurada en PROVIDER_API_URL"
  }
]
```

Este ejemplo es estructural: el teléfono incompleto se rechaza. Obtén el `artistId` en el área del artista. El servidor valida artista, formato, alcance, fecha, consentimiento, proveedor y selección para la sesión. El registro solo afirma evidencia preexistente: la aplicación no verifica SMS, identidad o titularidad por sí misma. Ese proceso tiene que realizarse antes del alta. Mantén la evidencia fuera del navegador y limita sus accesos.

## Reglas del puente Telegram

No existe webhook Telegram en esta app. El transporte directo usa getUpdates desde el servidor durante la consulta, con bloqueo global D1 y reply correlacionado. Las siguientes reglas de webhook solo aplican si se construye un puente externo independiente. **Nunca** uses «el último mensaje recibido».

Si implementas el puente bajo tu control:

1. Configura `setWebhook.secret_token` y verifica `X-Telegram-Bot-Api-Secret-Token` con comparación constante, además de `from.id` y `chat.id` numéricos fijados en el servidor. El nombre visible no es verificación de origen. No registres el token ni el texto.
2. Deduplica `update_id` y `message_id`. Acepta solo respuestas vinculadas mediante `reply_to_message.message_id` al mensaje enviado o mediante ID devuelto por el contrato autorizado. Rechaza respuestas antiguas, parciales y conversaciones ajenas.
3. Si el protocolo no permite correlación, serializa **globalmente en el puente**. Una consulta por sesión en esta app no sustituye una cola global para un bot compartido. Si ni siquiera con serialización puede distinguirse una respuesta tardía, no habilites ese protocolo.
4. No contestes automáticamente a los mensajes del bot proveedor: de esa forma no creas un bucle entre bots. No vuelvas a enviar una consulta por repetición de webhook.
5. Respeta `retry_after`, límites del proveedor y TTL. Usa almacenamiento duradero para correlación y borrado según su política; una variable en memoria de un Worker no sirve como cola global.

La [documentación de setWebhook](https://core.telegram.org/bots/api#setwebhook) describe el secreto de origen. Este documento es el contrato del adaptador y los requisitos pendientes; no describe el puente MTProto, documentado y probado por separado.

## Prueba de activación

Con un titular previamente autorizado, comprueba envío único de +34, respuesta de origen/conversación fijados, correlación real, duplicados, mensajes tardíos, errores, límites, borrado y representación segura en la nota. Conserva un acta sin datos personales. Solo después puede afirmarse «integración real comprobada».

# Seguridad y privacidad

## Controles implementados

- Identidad del artista autenticada por el gateway privado de Sites. El backend rechaza peticiones sin identidad y comprueba propietario de sesión. Las cookies de autenticación, su firma, expiración y atributos Secure/HttpOnly/SameSite pertenecen a la plataforma; esta app no crea tokens de login propios. Desarrollo local simulado con cookie HttpOnly/SameSite=Lax y Secure si usa HTTPS; no es autenticación de producción.
- Sesiones de actuación en servidor, máximo dos horas. UUID y CSRF aleatorio, del que solo se conserva SHA-256. Las consultas necesitan propiedad de sesión y CSRF correcto. Creación/borrado exigen Origin igual al origen de la petición y cuerpo JSON; no hay CORS permisivo.
- Autorización antes de cualquier proveedor: selección cerrada, móvil validado en servidor, artista, evidencia previa del titular, alcance, proveedor y vigencia. Demo admite únicamente las dos fichas sintéticas del almacén; nunca hace llamadas a Telegram.
- Detección automática tras 800 ms de estabilidad: solo fichas seleccionadas de una sesión preparada. Una solicitud automática por sesión/nota/número; errores y deshacer no disparan reintentos. Una respuesta reservada permanece exclusivamente en memoria y exige sesión/nota/revisión/generación vigentes al pulsar el gatillo. Cualquier edición la descarta.
- SQL parametrizado. D1 está solo en el servidor y no expone acceso público. No aplica RLS PostgreSQL: el aislamiento se comprueba en cada operación con el ID autenticado del usuario.
- Cinco preparaciones por artista/hora, veinte consultas por artista/hora, cinco por sesión/minuto y diez por sesión. Contadores persistentes D1 y adquisición atómica del turno; una consulta simultánea por sesión. No garantiza una cola global de un bot externo; el proveedor debe implementarla si la necesita.
- Cuerpo entrante limitado por lectura a 32 KB, nota a 20.000 caracteres y respuesta a 8 KB. Normalización duplicada en servidor. Las respuestas exigen requestId/teléfono exactos, `final: true`, campos de texto validados y límites.
- API sin reintentos automáticos, sin redirecciones, con HTTPS y tiempo máximo de 12 s. Resultado tardío descartado; sesión revocada revisada otra vez antes de devolverlo. Un fallo de red puede haber alcanzado el proveedor; no debe repetirse sin comprobar el ID.
- CSP con nonce aleatorio por respuesta, scripts propios y sin `unsafe-inline` en producción. Estilos inline permitidos para variables de viewport; objeto/base/form/frame restringidos. No-store, nosniff, no-referrer y política sin cámara/micrófono/geolocalización. HSTS en HTTPS. En desarrollo se añade `unsafe-eval` y WebSocket para HMR; no forma parte de la política de producción.
- Ningún token de proveedor o registro de consentimiento entra en el cliente. Las API no incluyen detalles del proveedor en errores. Los registros de aplicación emiten exclusivamente códigos de error constantes; no registran excepciones crudas, teléfonos, nombres ni resultados.
